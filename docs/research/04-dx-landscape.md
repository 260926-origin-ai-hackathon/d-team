## 2. 観点別の知見

### 観点1: 避難所運営支援システムの実態

- 防災DXサービスマップには248サービス、避難生活支援カテゴリに101件。カタログ上、価格・導入実績はほぼ「記載なし」で、大半がクラウド前提。オフラインを明記しているのは能美防災N-HOPSのみ（読めた範囲）。出典: https://bosai-dx.jp/ / https://bosai-dx.jp/catalog/shelter/
- デジタル庁R5実証（神奈川県、2023/10/23・2024/2/28）: マイナカード入所で90.2%の業務削減、定期報告50.7%削減、第2回は手書き比約9.6倍（顔認証約7倍、スマホ搭載約6.5倍）。約80名参加。出典: 内閣府「デジタル庁の取組み（資料1-2）」 https://www.bousai.go.jp/kaigirep/kentokai/dataplatform/pdf/gijutsu/r5/dai3kai/siryo1-2.pdf / https://k-tai.watch.impress.co.jp/docs/news/1597283.html / https://xtech.nikkei.com/atcl/nxt/news/24/00326/ 。日経xTECHは「実運用には県・市町村間の事前協定が必要」「能登では発災後に急遽仕組みを作る必要があった」と指摘。
- 熊本市くまもとアプリ: 紙0.86人/分 vs アプリ13人/分（約15倍）。171指定避難所、台風10号(2024/8)で約2,300人。課題: 「職員異動で研修が繰り返し必要」「住民の認知・導入が限定的」「マイナカードのプライバシー懸念」。出典: https://pocketsign.co.jp/casestudy/13

### 観点2: 能登半島地震2024で使われたデジタルツールと評価

- 「ピーク時に3万人いた避難所被災者が1月19日時点で1.5万人まで減少。しかし減った1.5万人のうち所在が確認できるのは2千名」。Suicaは「カードの携行率及びカード読取機の不足のため」採用（マイナカード対応のNFC Type Bリーダーが間に合わず）。志賀町は2/16に一次避難所全8か所(430名)へ導入完了。マイナカード携行率は約4割。輪島市の罹災証明オンライン申請は95%以上。出典: https://www.bousai.go.jp/kaigirep/kentokai/dataplatform/pdf/gijutsu/r5/dai3kai/siryo1-2.pdf / https://k-tai.watch.impress.co.jp/docs/news/1564171.html 。Suicaは発災から配布開始まで5週間以上（1/1→2/7）。
- BDX（防災DX官民共創協議会）は1/5に現地入り。避難所情報は1/8時点で1,598か所（重複・未確定あり）→1/28に917か所確定。被災者訪問アセスをオンライン化し3/21時点約4,900件。被災者DBは10以上のシステムを名寄せ。臼田氏の総括: 「防災DXは『魔法』ではなく『手品』…事前（平時）の準備が不可欠」「自治体間格差…基本的に低い方に合わさざるをえない」「情報を増やすだけでは情報過多→負荷増大。インテリジェンスへ」。出典: 防災科研 臼田「防災DXの現状と課題」 https://www.bousai.go.jp/jishin/syuto/taisaku_wg_02/4/pdf/siryo3.pdf
- 通信は「発災前と比較して最大約7割～8割のエリアで通信の支障」。Starlinkは3キャリア計660台を避難所・自治体・DMAT等へ貸与（総務省）。KDDI単独で350台＋約350台＝約700台。総務省整備の衛星インターネット機器は1,750台中423台使用。Starlink仕様: 下り40〜220Mbps、無線LAN同時接続128台、アンテナ6.9kg。応急復旧終了は1/18発表。自主点検レポート: 「発災当初は、各機関の担当者がシステムに不慣れなため、デジタル技術を十分に活用できない事例が見られた」。出典: 総務省 https://www.soumu.go.jp/main_content/000962902.pdf / KDDI https://newsroom.kddi.com/news/detail/xkddistarlink_350.html / 内閣府 自主点検レポート https://www.bousai.go.jp/jishin/noto/taisaku_wg_02/pdf/siryo4.pdf 。日本教育新聞は通信復旧に「3週間近く」と記述 https://www.kyoiku-press.com/post-273833/
- 内閣府 検証チーム第3回「避難所運営の状況」職員報告: 「在宅避難者や車中泊者を含めた避難者や避難所の状況の体系的な把握が困難」「避難者の要望を詳細に把握するまでに時間を要した」「各機関が把握している孤立集落の状況や各避難所の情報が一元的に集約されていなかった」。避難所調査・D24H（保健師）・県データ共有アプリ（自衛隊）の3系統が並走。出典: https://www.bousai.go.jp/updates/r60101notojishin/pdf/kensho_team3_shiryo02.pdf
- 現場体験談（石川県アーカイブ）: 「1月1日からここにいたのが800人から900人」を手書きで管理、「役所との連絡も携帯も全然通じない時もありました」、発電機設置は4日夕方、情報連絡係を約20グループに配置し朝9時・夕4時に連絡会。出典: https://noto-archive.pref.ishikawa.lg.jp/story/detail1
- 内閣府「災害対応の在り方」概要: 「広域避難者や自主避難所の避難者を含め、避難者の情報把握の在り方について制度改正も含めて検討」「SOBO-WEBを中核とした防災デジタルプラットフォームを可及的速やかに構築」。出典: https://www.bousai.go.jp/jishin/noto/taisaku_wg_02/pdf/gaiyo.pdf

### 観点3: 災害時AIチャットボット・生成AIの事例と限界

- SOCDAはLINE経由で安否・不足物資を自動抽出。令和元年台風19号で三重県・伊勢市が情報投稿機能を実利用（利用者は職員中心）。神奈川県実証（2021/2）は15市町の職員が住民役。千葉県はLINE上でFAQ型AIチャットボット（「スマホを充電したい」等）を運用。いずれもLINEサーバ＝通信必須。出典: https://www.lycorp.co.jp/ja/sustainability/jp/common/DisasterResponseEfforts_2310.pdf / https://robotstart.info/2021/02/19/socda-experiment.html
- 東武トップツアーズ「被災者支援AI」は約100制度をOpenAI APIで検索する検索AI。「ハルシネーションが起きづらい仕組みだが100%ではない」「引用元確認と各行政への問い合わせ推奨」と明記。出典: https://www.dx-tobu.com/notoai/
- NTT東日本×横須賀市は2026/8/31から生成AIで災対本部の意思決定支援を実証。目的は「経験浅い職員への支援」「ベテランの経験知継承」。文科省BRIDGEは能登の経験から「生成AIによる誤学習や誤情報生成等を防止…個人情報…安全性を確保するための技術開発が不可欠」として防災MRAGを防災科研で開発。出典: https://prtimes.jp/main/html/rd/p/000001345.000098811.html / https://www8.cao.go.jp/cstp/bridge/keikaku/r6-h02_bridge_r6.pdf 。国の方向性も「RAGで根拠を縛る」「個人情報を外に出さない」。ただしどちらも集中基盤前提で、避難所端末上で動く設計ではない。
- (検索結果のみ) 渋谷区生成AIチャットボット（2025/3開始）は2か月で10万件、解決率77%。停電時、携帯基地局の非常用電源は「数時間〜1日から2日程度」 https://news.mynavi.jp/article/20240808-2999614/
- 限界（共通点）: 通信必須（LINE/クラウドAPI）、ハルシネーション（ベンダー自身が「100%ではない」）、回答範囲が制度案内・FAQに限定、住民アプリの認知率依存。

### 観点4: オフライン/エッジで動くAI・ローカルLLMの防災活用

- Pocket RAG（arXiv 2602.13229、2026/1）: Android上のSLM＋Hybrid RAGで応急手当ガイダンス。精度94.5%（身体的応急手当）/97.0%（心理的支援）、応答14.2秒→3.7秒。動機は「災害現場や遠隔地で第一対応者がネット接続を失う」。 https://arxiv.org/abs/2602.13229
- TRIDENT（arXiv 2512.10741）: 災害時の完全オフライン運用を想定し、「病院・避難所・緊急対策拠点に事前配置したエッジ計算資源」でトリアージ能力を維持する構想。 https://arxiv.org/abs/2512.10741
- LLM×災害管理サーベイ（arXiv 2501.06932）: ハルシネーション、オフライン/エッジ配備制約、リアルタイム性、高リスク下の信頼性を課題として整理。 https://arxiv.org/abs/2501.06932
- オフグリッド市民緊急通信（arXiv 2509.22568）: LoRa＋スマホアプリ、1.2kmで92%パケット到達率。 https://arxiv.org/abs/2509.22568
- SafeGuardian-LLM（GitHub）は「オフライン機能」を掲げるが中核はGemini API。 https://github.com/Ashoka74/SafeGuardian-LLM
- 国内: 「ローカルLLM×避難所」の自治体実証・論文は今回の検索では見つからず（未確認）。

### 観点5: 避難所のPC・電源の実態

- 内閣府調査（R6.11.1時点、指定避難所82,820か所）: 非常用発電機等 **61.1%**（50,609か所）、通信設備 61.1%、冷房74.3%、暖房77.9%、ガス69.4%、飲料水68.7%、入浴洗濯用水22.2%。出典: https://www.bousai.go.jp/taisaku/hinanjo/pdf/r7_0123.pdf / https://www.gas-enenews.co.jp/lpgas-lng/47542/
- 文科省調査（R6.11.1時点）: 公立学校32,186校中29,529校（91.7%）が避難所指定。うち非常用発電機等 **77.2%**、通信設備85.3%、冷房85.5%、暖房86.3%。体育館の冷房設置率は約2割。 https://www.mext.go.jp/content/20250714-mxt_bousai-000042903_1.pdf
- GIGA端末の「災害時・非常時の持ち帰り」準備率: 実施できる64.3%、準備中31.9%。避難所での運営転用事例は未確認。 https://www.mext.go.jp/a_menu/other/mext_00921.html
- デジタル庁R6実証（石川県）の職員意見: 「そもそも電源、電波がないと使い物にならない」「避難所ごとにPC、カードリーダー等を配備するのは難しい」「避難所用パソコンやインターネット環境が整っていない避難所も多い」。通信途絶シナリオでは職員26名全員がStarlink＋可搬電力を有益と回答。出典: https://www.digital.go.jp/assets/contents/node/basic_page/field_ref_resources/7a1718f5-d5d1-483e-85db-76d2734bf9dd/e86c2bff/20250422_policies_disaster_prevention_outline_02.pdf
- ノートPCローカルLLMの要件（SIOS Tech Lab）: 7-8Bモデルで16GB RAM推奨、3-4Bで8GB、Q4_K_M量子化でメモリ約75%削減。長時間は発熱・バッテリー駆動で性能制限。 https://tech-lab.sios.jp/archives/50797
- (検索結果のみ) 文京区は全避難所にタブレットを配備 https://www.bousai.go.jp/taisaku/hinanjo/pdf/r6_seikatsukankyou_jirei.pdf

### 観点6: 防災DXが現場に定着しない理由

## 3. この観点でのまとめ

1. 避難所DXの主戦場は「受付・名簿・状況報告」で、マイナカード受付は9割削減・15倍速と効果が実証済み。ただし全てクラウド＋通信＋端末前提。
2. 能登では通信が最大7〜8割のエリアで途絶し、Starlink 660台が届くまで避難所は「携帯も通じない」「手書き800人」の世界だった。
3. Suica配布は発災から5週間後に開始。マイナカードはリーダー未整備で使えなかった。「誰がどこにいるか」は最後まで課題。
4. 国（デジタル庁・防災科研）は通信途絶対策をStarlink＋可搬電源で解いており、「端末側で完結する」設計は選択肢に入っていない。
5. 職員の本音は「電源・電波がないと使い物にならない」「有事にしか使わないシステムは使いこなせない」「全避難所にPCは置けない」。
6. 生成AI活用は制度案内チャットボット（クラウドAPI）と災対本部支援（横須賀実証）に限られ、ベンダー自身が「100%ではない」と明記。
7. 国のBRIDGE事業は「RAGで根拠を縛る」「個人情報を外に出さない」を要件化しており、ローカルLLMの設計思想と整合する。
8. 海外研究（Pocket RAG、TRIDENT）はオンデバイスSLM＋RAGで応急手当・トリアージを扱い、「避難所への事前配置」を明示的に提案。国内の同種実証は未確認。
9. 指定避難所の非常用電源は61.1%、学校避難所では77.2%（通信設備85.3%）。ノートPCが動く電源は過半の避難所にある。
10. 外国人対応は「翻訳アプリはあるのに避難所で多言語表示を見た人がゼロ」という運用の問題。ツールより「その場で誰でも使える」ことが重要。

## 4. オフラインのローカルLLMが先行事例と差別化できる点／実現可能性／リスク

**差別化できる点**
- 空白の3日〜3週間を埋める: 先行事例は全て通信必須。能登の通信途絶の間に動くAIは事実上存在しない。Starlink到達前・非対応避難所向けの唯一の選択肢になれる。
- 「受付」ではなく「問い合わせ応答・判断支援」: 101件の避難所支援サービスは名簿・混雑・備蓄が中心。墨田区提言が求める「問い合わせが職員に集中して現場に人が割けない」への解を狙える。
- 初見でも使える: 自然言語対話はUI学習コストが最小。「進行補助が横にいないと運用は難しい」というギャップをAIが補助役として埋められる。
- 個人情報が端末外に出ない: BRIDGEが要件化した安全性確保を構造的に満たす。
- 多言語: 「多言語表示が現場に出ない」問題を、避難者が自分の言語で聞ける形にできる（ローカル小型モデルの多言語精度は要検証）。

**実現可能性の根拠**
- 電源: 指定避難所の61.1%、学校避難所の77.2%に非常用電源等。
- 端末: GIGA端末は災害時持ち帰り準備64.3%（多くはChromebook/iPadで7Bクラスは不向き。避難所常備ノートPC1台という前提の方が現実的）。
- モデル: 3-4Bで8GB、7-8Bで16GB RAM（Q4量子化）で動作。Pocket RAGはスマホ上のSLM＋RAGで94.5%精度・3.7秒応答。
- 情報源: デジタル庁は避難所PoCの設計書・ソースコード・データモデルを公開方針。内閣府ガイドライン、自治体マニュアル、支援制度一覧（約100制度）などRAGに載せる公的文書は既に存在。
- 政策整合: 内閣府「在り方」は「防災DXの加速・新技術等の活用推進」「デジタル利用を前提としたTTX」を掲げ、横須賀市実証も「マニュアルを参照させて優先順位を提示」と同型。

**リスク**
- ハルシネーション: RAG＋出典表示＋「行政窓口へ確認」の常時表示が最低要件。
- 小型モデルの日本語・多言語精度: 「やさしい日本語」生成・ベトナム語等の品質は未検証。
- 端末の熱・電力: 避難所の電源は照明・暖房・充電と競合する。
- 情報の鮮度: 「静的知識（マニュアル・制度）」と「動的情報（誰がどこに・物資）」を分け、後者は手入力に限定する設計が必要。
- 定着: 平時利用（訓練、マニュアル検索、研修）を組み込まないと「担当者がシステムに不慣れ」を再現する。
- 責任分界: 職員不在時に住民が運営する現実と、AI回答の責任の所在。
- 差別化の持続性: BRIDGEやStarlink常備が進めば「オフライン」の優位は縮む。「Starlinkが来るまでの72時間」「Starlinkがない小規模避難所」に絞った位置づけが妥当。

**未確認・取得不可**: NTT避難所受付支援サービスの内容、各社製品の価格、SOCDA導入自治体総数、NEC LLM被災状況把握レポート（403）、VoiceTraの避難所での定量実績、GIGA端末の避難所転用事例、ローカルLLMのノートPC消費電力実測、国内のローカルLLM×避難所実証。
