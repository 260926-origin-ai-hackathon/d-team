# 避難所AI — 提供方法の検討（自治体ネットワークの制度・避難所の実態・先行事例から）

作成: 2026-09-25（Claude Code による Web 調査の統合。一次資料は総務省・デジタル庁・内閣府・自治体の公開文書。「本文確認」と「検索要約のみ」を区別してある。推測は【推測】と明記）
問い: **こちらがマシン（DGX Spark 級の専用機）ごと提供すべきか、市役所のPCに簡単に入れられるようにすべきか。**
関連: `事業展開とマネタイズの選択肢.md`（財源・課金）／`避難所AI_サービス概要（自治体向け）.md`

## 0. 結論（先に）

**二択のどちらでもない。「自治体が資産として持つ防災専用のスタンドアロン Windows ノートPC」を本線にし、ソフトはそこに入れるパッケージとして提供する。** マシン提供は次の2形態に限る。

1. **実証期の持ち込み機**（こちらの機材を訓練・実証で使ってもらい、本導入時に自治体資産へ移す）
2. **地元SIer・防災ベンダー経由のキッティング済み一式**（ノートPC＋ルーター＋蓄電池。保守は相手が持つ）

DGX Spark 級のアプライアンスは**避難所には置かない**。置くなら災害対策本部の1台構成（上位モデル）に限る。

理由を一言で: 職員の業務端末は制度上使えない（§1）、避難所に運営用PCは常備されていない（§2）、自治体でのアプライアンス採用例はゼロで、先行事例はすべて「AIソフト＝スタートアップ／基盤＝大手・流通／保守＝地元SIer」の分業（§3）。

## 1. 制度: 自治体ネットワークの三層分離とセキュリティポリシー

出典の中心は総務省「地方公共団体における情報セキュリティポリシーに関するガイドライン」**令和8年3月版**（2026-03-27 改定、以下 GL）https://www.soumu.go.jp/main_content/001068239.pdf （本文確認）

### 1-1. 枠組み
- GL は「技術的助言」。拘束力を持つのは**各自治体が定めるセキュリティポリシー**。改正地方自治法（令和6年）で自治体に方針の策定・実施が義務化され（244条の6）、総務大臣指針は GL の基本方針相当。→ 最終判断は各自治体の CISO と情報政策担当課
- **三層の構え**（平成27年 総務省通知由来）: マイナンバー利用事務系／LGWAN接続系／インターネット接続系。α（主端末を LGWAN 系）、β（主端末をインターネット系）、β'（重要資産もインターネット系）
- 令和8年3月版の改定は大臣指針との重複削除・機器廃棄とデータ消去・USB リスク・DNS 対策で、三層・無線LAN・持ち出しの規定は令和7年3月版から実質変更なし

### 1-2. 職員の業務端末で何ができないか
| 規定 | 中身 | 避難所AIへの意味 |
|---|---|---|
| (17) 無許可ソフトウェアの導入禁止 | 統括情報セキュリティ責任者と情報システム管理者の許可が要る | Ollama・FastAPI を職員PCに入れるには許可手続き |
| (13) 無線LAN | LGWAN 系はクライアント証明書（EAP-TLS 等）による機器認証が必須、端末間通信禁止、許可 SSID 以外に接続不可 | **避難者の不特定スマホは「正規端末」ではない**ので、LGWAN 系・マイナンバー系の無線LANに入れられない |
| (19) 業務外ネットワークへの接続禁止 | 「支給端末を、定められたネットワークと異なるネットワークに接続してはならない」「OS ポリシーで技術的に制限することが望ましい」 | 職員PCをホットスポット親機にする構成はこれと正面衝突【解釈】 |
| 注17・注18 | 支給端末以外の庁内接続は個別許可＋事前検疫＋記録。無許可の持ち込み端末の AP 接続を禁止 | 不特定多数の住民端末を一括収容する運用はこの枠に収まらない |
| 物理的セキュリティ | 機密性2以上を扱う管理区域に個人所有の端末・通信装置を持ち込ませない | — |
| **テザリング／ホットスポット／モバイルルータ／スタンドアロン** | **GL 全文（422ページ）に語として0件** | 明文の許可も禁止も無い。解釈は各自治体 |

### 1-3. 住民向けの通信提供は想定されている
- GL 解説 6.1(4) 注6: 「**庁舎内で住民、観光客に公衆通信回線を提供する場合は、内部の情報システムとネットワークを切り分け、不正アクセスを防止する対策を講じなければならない**」
- 避難所 Wi-Fi は総務省「公衆無線LAN環境整備支援事業」（防災拠点）として業務系と別枠で制度化。内閣府の避難所運営ガイドライン（2024-12）も「平時から各避難所に Wi-Fi 等の情報入手手段を確保」を求める
- → **避難所AIの Wi-Fi は「業務端末への不特定端末接続」ではなく「公衆通信環境の提供」として整理すれば筋が通る**。条件は内部システムとの完全な切り分け

### 1-4. 災害時の特例は無い
- GL 7.4 例外措置: CISO 許可で可。緊急時は事後報告で可（「不可避のとき」に限る）
- ICT-BCP ガイドライン（総務省 2024-03）: 人命に関するシステムは一時的なセキュリティ緩和も必要、ただし時限・周知・復帰確認
- → **災害時に三層や無線LAN要件を解除する明文の特例は存在しない**。平時に配備するシステムの根拠を「緊急時例外」に置くことはできない

### 1-5. スタンドアロン PC の扱い
- 「三層固有の要件（系統間通信制御・無害化・証明書認証・セキュリティクラウド参加）」の外にはなるが、**セキュリティポリシーの外ではない**【解釈】。適用されるもの: 情報資産としての登録、持ち出し許可制と記録（4.4）、ソフト導入許可(17)、不正プログラム対策（ネット非接続でも導入・更新義務）、無線LAN一般要件（WPA2/3）、住民向け通信の切り分け（注6）、廃棄・データ消去（令和8年3月版で強化）
- GL 注3「**持ち出し専用パソコン**」の運用が避難所PCの雛形になる: 平時は情報を置かない／持ち出し時に必要最小限だけ記録／返却時に完全削除／第三者が物理アクセスしやすい環境では **USB ポートを物理封印またはシステムで無効化**／ディスク暗号化

### 1-6. 生成AI・ローカルLLMの規範
- デジタル庁 DS-920「生成AIの調達・利活用に係るガイドライン」2.0版（2026-09-01 施行、自治体は参考扱い）: オンプレ・ローカル推論に固有の規定は無し。約款型クラウドには要機密情報を入れられない、が中核
- 総務省「自治体における AI 活用・導入ガイドブック」第4版（2025-12）: 稼働環境の類型に「E 庁内環境にオンプレミスで構築」を明記。別添の「生成AIシステム利用ガイドライン（ひな形）」は「**情報政策担当課が指定する生成AIシステム以外の利用は禁止**」「システムごとに入力可能な情報を機密性分類で別表に定める」
- 総務省 自治体AI利用WG（2025-06 骨子）: 「LLM をダウンロードしてローカルネットワーク内で運用する場合や、LLM がスマホや PC に搭載されている場合のセキュリティ対応も検討する必要」。要機密情報をローカルで扱うことへの肯定的意見はあるが**ガイドライン未反映**
- → 避難所AIは自治体の「指定システム」として登録し、避難者名簿（自治体機密性 3B/3C 相当）を扱う範囲を別表で定める、という手続きになる。可否は各 CISO の判断

### 1-7. 制度面の評価
| 動かす場所 | 実現性 | 理由 |
|---|---|---|
| (a) 職員の既存業務端末 | **低** | (13)(19) と正面衝突。緊急時例外は平時配備の根拠にならない |
| (b) 自治体資産の防災専用スタンドアロン PC | **中〜高** | 三層固有要件の外。住民向けは公衆通信環境として切り分け。持ち出し専用PC運用＋指定システム登録で整理できる |
| (c) 事業者が用意した機器の持ち込み | **中** | 自治体ネットに繋がなければ接続許可は不要。ただし職員が使うなら「支給端末以外」の規定（機密性3は支給端末以外で禁止）にかかる。**実証→自治体資産化（貸与・寄贈）の移行経路**として位置づける |

## 2. 現場: 避難所に運営用PCは常備されていない

出典の中心: 内閣府「令和6年能登半島地震における避難所運営実態調査報告」（2026-03）https://www.bousai.go.jp/taisaku/hinanjo/pdf/r6notojishin_hinanjo_chousa.pdf ／志賀町 対応検証報告書 https://www.town.shika.lg.jp/uploaded/attachment/1793.pdf ／内閣府 別添資料1 https://www.bousai.go.jp/oyakudachi/pdf/cloud/02/betten1.pdf（いずれも本文確認）

### 2-1. 実際に誰のPCが使われたか
| 避難所 | PC | 通信・電源 |
|---|---|---|
| 珠洲市 宝立小中学校（避難者 800〜900人） | 手書き名簿 → **校長からPCを借用**、入力は福井県の応援職員 | 停電 1/8 まで、通信途絶 1/13 まで |
| 珠洲市 馬緤町 自然休養村センター | 住民の運営事務局が**自分で用意したPCの Excel** | 通信途絶 1/10 頃まで。USB で市役所へ渡そうとしたが**市役所側のセキュリティで外部USB不可**、LINE で報告 |
| 志賀町（役場・避難所） | 企業貸与: ノートPC 20＋30＋10台、iPad 20台、デスクトップ5台、プリンタ 20台、Wi-Fi 機器 | デジタル情報課の業務に「職員用端末器確保」 |
| 熊本地震（2016）益城町・熊本市 | 連絡は当初**私用電話**、5月中旬以降に**国から無償提供されたタブレット** | 益城町は全域停電 4/19 まで |
| 志賀町 Suica 受付 | JR東が Suica 2.1万枚＋リーダー 350台を無償提供。導入完了は**発災 37 日後** | マイナカードは携行率と読取機不足で断念 |

- 内閣府の公式な想定（別添資料1）: 避難所端末の確保は「**職員が自分の端末を持参（職場からの持参を含む）**」か「**避難所に端末を保管しておく**」の2通り。ネット不可時は「PC 端末のみのスタンドアロン方式で入退所管理を行える（名簿は庁舎に送れない）」
- 八王子市の避難所運営マニュアル（2022-10）: 職員の携行品は職員証・スマホ・携帯ラジオ。**PC は無い**。開設時チェックに「庁内LANで構築されたPCが使えるか」
- 学校のネットワーク: 内閣府は学校 Wi-Fi の避難所利用に「事前に教育委員会・学校と協議」「開設時に一般開放する設定変更」を要求。文科省の教育情報セキュリティポリシー GL（2025-03）に避難所運営への校務端末利用の明文規定は無い。GIGA 端末の避難所転用事例は見つからず

### 2-2. デジタル庁のモデル仕様書はクラウド前提
- 「避難所運営システム モデル仕様書」（2023-12 版・2024-11 改訂案、xlsx 本文確認）: **「オフライン」の語が無い**。データは「デバイス内に保有せず、クラウド環境で保有」。管理者側は「インターネットで動作すること」。端末の調達主体の規定は無い
- 令和7年度「マイナンバーカード避難者受付アプリ」（2026-02）は「電波が無い場所でも使える」を掲げ、避難所は **Android タブレット**、本部は PC。名張市で実証
- 令和4年度実証の職員意見: 「ネット通信環境が遮断した場合に使い物にならない」「電源の確保（避難者側のスマホの電源も）」

### 2-3. 財源: PC 単体は緊防債の「非適債」
- **緊急防災・減災事業債**（充当率100%・交付税算入70%、**令和12年度まで延長**）の対象: 指定避難所の生活環境改善（トイレ・空調・**Wi-Fi（衛星通信サービスを含む）**・ポータブル蓄電池等）、防災情報システム、災害時オペレーションシステム。Wi-Fi の「制御・監視装置、電源設備、伝送路設備」は AP と併せて整備する場合に対象
- **「個別端末整備」は非適債 → 特別交付税（措置率0.7）、しかも貸与に限る（譲渡は対象外）**（内閣府 siryo39_1、消防庁 手引き 令和7年度版 p62-63、本文確認）
- 奥能登デジタル地域拠点整備（2市2町・14拠点・Starlink＋蓄電池＋避難所管理システム＋サイネージ）は総務省「地域社会DX推進パッケージ」補助で**事業費 1億4,400万円**（国 7,200万・市町 5,200万・県 2,000万。検索要約のみ、要原典確認）
- → **PC 単体で財源を立てるより「避難所 Wi-Fi（衛星通信）＋蓄電池＋受付システムのセット」として提示する方が枠に乗る**。奥能登がそのモデル

### 2-4. 現場面の評価
| 動かす場所 | 実現性 | 根拠 |
|---|---|---|
| (a) 職員の持ち込みPC | 低〜中 | 内閣府は「持参」を想定するが、携行品に PC が無い自治体もある。職員が到着できず開設が遅れる例（高岡市）。GPU 機はまず無い |
| (b) 学校PC | 低（緊急代替の実績のみ） | 校長PC借用の実例はあるが、校務用PCは児童生徒の個人情報を持ち教育委員会のポリシー下 |
| (c) 自治体が事前配備する防災専用PC | 中 | 「避難所に端末を保管」は内閣府の公式想定。奥能登・珠洲市が常設機材の先行例。財源は Wi-Fi セットに組み込む工夫が要る |
| (d) 事業者提供の機器 | 中〜高（短期・実証） | 企業貸与・無償提供の実績が最も多い。ただし発災後の貸与は到着に数週間かかる。平時からの常設が前提 |

## 3. 市場: 提供形態の先行事例

出典: 総務省「自治体における生成AI導入状況」（令和7年6月）https://www.soumu.go.jp/main_content/001018084.pdf ほか（各行に併記）

### 3-1. 自治体の AI 導入の型
- 導入済 514 市区町村のうち「専用の生成AI環境を構築」は 88 件（1割弱）。**導入コスト0円が最多（669件）**、課題1位は「人材不足」
- オンプレ事例: **宮崎県**（HPE サーバ＋Sparticle GBase＋保守は地元 南日本ネットワーク。調達は「賃貸借＋保守」の1年契約。災害対応チャットボットへ拡張予定）https://prtimes.jp/main/html/rd/p/000000212.000045092.html ／**山口県×NTT西日本**（小型GPUサーバで tsuzumi オンプレ実証）
- 国も GPU 基盤は「賃貸借＋保守」で調達（特許庁 AI 基盤 16.3億円、2026-05 落札）
- **自治体が DGX Spark を名指しで調達した公告・採用事例はゼロ**（大学のみ）。日本価格 70〜120万円、保証は1年センドバックのみ。自治体の PC 調達の定型「5年賃貸借＋キッティング＋オンサイト保守＋返却時データ消去」（枚方市・鳥取県・佐賀県教委の仕様書）と噛み合わない
- Sparticle「GBase on Spark」が SB C&S 経由で流通開始（2026-06、自治体を想定顧客に明記）。アプライアンス路線は既に流通大手が走っている

### 3-2. 端末込みの防災システム
- 避難所受付端末セット: ハートネットワーク（タッチパネルPC＋ICリーダー、基盤は GCP、新居浜市）、テレネット「らくらく避難所くん」（専用スマホ端末、無料プラン3年、養父市・豊中市・三田市）、**FORTE「ネットワーク環境不要 避難所受付支援システム」**（管理PC＋専用タブレット＋Wi-Fi ルータ、「電源さえあれば使用可能」、大垣市）
- 相場: ヴァカン 初期 40万円〜＋月 93,400円〜、ロカポ「マイ避難所DXライト」導入 99万円＋月 3.3万円〜（いずれも検索要約）
- 戸別受信機の型: 売り切り＋協力店設置＋「市は責任を負わない」の責任分界（長野市 1台4万円）

### 3-3. スタートアップの入り方
- **AIソフト＝スタートアップ／基盤＝大手・流通／現場保守＝地元SIer・販売会社**の三層分業が最頻（宮崎県、NEC cotomi→大塚商会「美琴」、JAPAN AI→大塚商会 OEM、Spectee→インフォコム 代理店→資本提携、Sparticle→SB C&S）
- 直販で広がった例もある: QommonsAI（1,000アカウント無料・代理店なし・約650自治体）
- **ソフト無償でも広がらなかった例**: 西宮市発「被災者支援システム」は J-LIS が無償配布したが、HW・導入・初期データが自治体負担のため**未導入 650 団体超**
- 入札参加資格は「1年以上の事業継続＋決算」が一般要件 → 学生チーム単独の入札は困難。入口はトライアル発注・随意契約・実証
- ネット無しでライセンス認証が完結する仕組みは公共向けに商品化済み（Adobe Acrobat FRL-Offline、自治体採用多数）

## 4. 提供形態の比較

評価軸: 制度（§1）／現場（§2）／財源（§2-3）／保守と責任／こちらの体力（学生チーム）／ピッチでの説明しやすさ

| 形態 | 制度 | 現場 | 財源 | 保守・責任 | こちらの体力 | 総合 |
|---|---|---|---|---|---|---|
| **A. 職員の業務PCにインストール** | × (13)(19) 衝突 | △ PC が来ない | ○ 追加費ゼロ | △ 自治体の情シスが嫌がる | ○ | **採らない** |
| **B. 学校PCにインストール** | × 教委ポリシー | △ 借用の実績のみ | ○ | × 責任分界が曖昧 | ○ | **採らない** |

### 4-1. なぜ C が本線か
1. **制度**: 職員端末は使えず、スタンドアロンの防災専用機は「持ち出し専用パソコン」運用と「公衆通信環境の切り分け」で GL と整合する唯一の形（§1-5, 1-7）
2. **現場**: 内閣府が「避難所に端末を保管しておく」を公式に想定し、奥能登・珠洲市が常設に動いている（§2-1）
3. **台数**: 通信途絶が価値の前提なので避難所ごとに1台要る。1自治体 20〜50か所なら 100万円級は成立せず、市販ノート十数万円しか置けない（`事業展開とマネタイズの選択肢.md` §8）
4. **先行事例**: ソフト無償でも「HW と導入が自治体負担」だと広がらない（被災者支援システム）。だから C 単体で終わらせず D（キッティング）と F（OEM）で導入労力をゼロに近づける
5. **体力**: 学生チームは入札資格・保守窓口・在庫を持てない。三層分業の「AIソフト」の位置に入るのが先行事例の型

### 4-2. マシン提供をやる場面
- **G（実証）**: 訓練でこちらの OmniBook を持ち込み、名簿はダミーデータのみ。本導入時に自治体が同等スペックを購入するか、機材を貸与・寄贈して資産化
- **D（一式）**: 地元 SIer や通信事業者（ソフトバンクは Starlink＋Wi-Fi の避難所キットを全国配備済み）に、ノートPC＋トラベルルーター＋蓄電池＋印刷 QR のキットとして載せてもらう。保守と責任分界は相手。戸別受信機の「協力店設置」の型
- **E'（本部1台）**: 市の災害対策本部で全避難所の名簿集約・大きいモデルで要約する上位構成。DGX Spark 級はここに限る。GBase on Spark が同じ場所を狙っているので、差別化は「避難所側と同じデータ形式で繋がる」こと

## 5. 製品側で満たすべき要件（設計へ反映）

制度と現場の調査から、避難所AIのパッケージが「自治体資産の防災専用PC」で受け入れられるための要件。現行実装（`shelter/`・仕様書 v1.0）との差分を書く。

| 要件 | 根拠 | 現状 | やること |
|---|---|---|---|
| ネットワーク分離: 内部システムと完全に切り離す | GL 注6 | Ollama は localhost のみ、Wi-Fi 側は FastAPI だけ | 既に満たす。「自治体ネットに一切繋がない」を導入手順書に明記 |
| 持ち出し専用PC運用: 平時は個人情報を置かない、返却時に完全消去 | GL 注3 | 名簿は SQLite | **「訓練モード（ダミーデータ）」と「本番終了時のワイプ」ボタン**を追加 |
| USB ポート封印／無効化、ディスク暗号化 | GL 注3 | 仕様書に BitLocker のみ | 導入手順書に USB 無効化（グループポリシー）と BitLocker を入れる。USB を使わない前提なので名簿の持ち出しは QR か LAN 経由 |
| ネット無しでの更新（OS・モデル・アプリ） | GL 不正プログラム対策、Acrobat FRL の前例 | 未対応 | **オフライン更新パッケージ**（署名付き zip を LAN か媒体で適用）。ライセンス認証を要求しない設計 |
| 指定システム登録: 入力可能な情報を機密性分類で定義 | 総務省ひな形 GL | 未対応 | 「避難者名簿（3B/3C）は端末内 RAG にのみ投入、外部送信は復旧時の本部同期だけ」を**データ取扱い仕様書**として1枚出す |
| 職員が来なくても動く | デジタル庁実証の職員の声、高岡市 | PIN 1つ | 自主防災組織の住民が電源を入れるだけで受付画面が出る「キオスク起動」 |
| 平時利用 | 「有事にしか使わないシステムは使いこなせない」 | マニュアル RAG あり | 訓練モードを平時の防災訓練・研修の標準メニューにする |
| **GPU 無し PC で動く** | 避難所に GPU 機は存在しない（§2-4）、自治体調達は汎用ノート | **未検証** | Core Ultra の iGPU/NPU、または CPU のみで qwen3.5:4b／2b を計測し、**最低推奨構成（例: 16GB RAM・Windows 11・GPU 不要）**を決める。これが無いと C は語れない |
| 電源 | 学校避難所の非常用電源 77.2%、蓄電池は緊防債対象 | — | 消費電力を実測し「ポータブル蓄電池 X Wh で Y 時間」を出す |
| 名簿の持ち出し | 馬緤町の「USB 不可」 | outbox に CSV | LAN 経由の本部同期（実装済み）を主、USB は使わない |
