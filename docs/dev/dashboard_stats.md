## 0. 一言で

ダッシュボードの先頭に **「対応の優先順」** の一覧（名簿の「伝えたいこと」「要配慮」と、避難者の声の「未対応」「緊急」を **人を単位に 1 本** に束ね、5 段階で並べる）と、**内訳の自動集計**（想定地区の割合・日本語以外の人数・支援が要る世帯・受付の方法）を足す。AI は使わない（ルールで数える・並べる）。同じ値を `eei.json` に氏名抜きで足し、本部へそのまま渡せるようにする。

## 1. 元データ（いまのコードで確定しているもの）

| データ | どこ | 単位 | 集計に使う列 |
|---|---|---|---|
| 名簿 | `evacuees` | 受付 1 件＝世帯（代表者＋同行者 `members`） | `needs`（伝えたいこと 10 択・世帯単位）、`care`／`members[].care`（要配慮・人単位）、`addr`、`lang`（世帯単位）、`hh`、`source`、`checked_in_at`、`updated_at` |
| 対面対応のメモ | `contacts` | 受付番号ごと・時刻付き | `evacuee_id`、`created_at` |
| 避難者の声 | `chat_logs`（`role='user'`） | 発言 1 件 | `kind`（question／request／trouble／emergency）、`topic`、`status`（open／done）、`outcome`、`evacuee_id`（登録済み端末なら受付番号、匿名なら NULL）、`created_at` |
| 設定 | `settings` | key/value | 備蓄量 `stock_*`（既存）。**新規 `area_towns`（想定地区の町名）** |

既存の集計（触らない）: `stats.summary()`（人数・性別・乳幼児・65 歳以上・要配慮区分・アレルギー・言語・ペット）、`stats.supplies()`（不足物資）、`voices.summary()`（避難者の声の件数）。

## 2. 集計の全体像

```
stats.summary()      既存  人数・要配慮・言語 …            → 上段の数字（そのまま）
stats.breakdown()    新規  想定地区／日本語以外／支援が要る世帯／受付の方法   → 内訳カード・eei.json
priority.items()     新規  対応の優先順（人を単位に 1 本）   → 先頭の一覧・/staff/priority・eei.json（氏名なし）
priority.counts()    新規  レベル別の未対応件数            → 先頭のチップ・eei.json
voices.summary()     既存  未対応の要望・困りごと・答えられなかった質問       → 避難者の声カード（そのまま）
```

- 全部 **SQLite を読んでその場で数える**（数十〜数百件なら一瞬。キャッシュも新しい表も作らない）
- 新しい表は作らない。「対応済み」は既存の `contacts` と `chat_logs.status` から判定する（§3.4）
- AI は使わない。理由: CPU では遅い・小さいモデルが例を写す記録がある（保管庫の提案と同じ）。並べ替えの根拠が「登録したとおり」になるので、審査で「なぜこの順か」に答えられる

## 3. 対応の優先順（`shelter/priority.py`・核）

### 3.1 行の単位

- **受付 1 件（世帯）＝ 1 行**。代表者と同行者の理由をまとめる（同行者に受付番号は無いので、行は代表者の受付番号で立てる）
- **匿名端末の相談＝発言 1 件 1 行**（受付番号が無いので束ねられない。「匿名」と表示）
- 退所済みの世帯は出さない

### 3.2 理由の種類とレベル

レベルは 5〜1。**1 行のレベル＝その行の理由の最大値**。理由は全部並べる。

| レベル | 表示 | 色 | 入る理由 |
|---|---|---|---|
| 5 | 至急 | 赤 | 伝えたいこと `dialysis`（透析）`oxygen`（酸素・医療機器の電源）／緊急ガードに掛かった相談（急病・暴力）で未対応 |
| 4 | 急ぎ | 橙 | 伝えたいこと `medicine`（薬が無い）`doctor`（診察が必要）／要配慮 `MED`（本人・同行者） |
| 3 | 今日中 | 黄 | 伝えたいこと `baby`（粉ミルク・おむつ）／要配慮 `ILL` `PRG` `NUR`（本人・同行者）／話題が `medical` の未対応の要望・困りごと |
| 2 | 様子見 | 緑 | 伝えたいこと `mobility` `diet` `family`／要配慮 `DIS` `INF` `ALG`／75 歳以上の人がいる／その他の未対応の要望・困りごと |
| 1 | 声かけ | 灰 | 伝えたいこと `sleep`（不安・眠れない）`language`（日本語不可） |

- 伝えたいことのレベルは **既存の `NEEDS_URGENCY`（`standard_form.py`）をそのまま使う**（透析・酸素 5／薬・診察 4／粉ミルク 3／移動・食事制限・家族 2／不安・日本語 1）。保管庫の提案表と同じ
- 要配慮のレベルと「75 歳以上」は新しい定数 `CARE_LEVEL`・`ELDERLY_LEVEL_AGE = 75` を `priority.py` に置く（75 は運営者の助手「要配慮者の洗い出し」`ai_staff._needs_care` と同じ線）
- **答えられなかった質問（`outcome='none'`）は一覧に入れない**。人への対応ではなく「案内・お知らせに載せる」で解決するものなので、避難者の声カードの「答えられなかった質問」に残す（保管庫の提案ではレベル 1 に入れていた → 本書で外す。未決 §9）
- 「トリアージ」「黒タグ」などの言葉は画面・コード・コメントに書かない

### 3.3 並び順

1. レベル降順
2. 同じレベルは **待たせている時間が長い順**（`since` が古い順）。`since` ＝ その行の未対応の理由のうち一番古い時刻（名簿由来は `evacuees.updated_at`、相談由来は `chat_logs.created_at`）
3. 同じなら受付番号の昇順

### 3.4 「対応済み」の判定（新しい表を作らない）

| 理由の出どころ | 未対応 | 対応済みになる操作 |
|---|---|---|
| 名簿（伝えたいこと・要配慮・75 歳以上） | その受付の **最新の対面対応メモが無い、または `updated_at` より古い** | 個人ページ `/staff/roster/{id}` で「対面対応のメモ」を書く |
| 相談（避難者の声） | `chat_logs.status='open'` かつ `kind` が request／trouble／emergency | 避難者の声の「対応済み」ボタン（既存 `voices.set_status`） |

- 名簿の理由は **登録内容が変わるたびに再び未対応に戻る**（本人がスマホから内容を直す・職員が編集する → `updated_at` が進む）。「新しい申告は見直す」という意味で妥当。職員の軽微な編集でも戻るのは許容する
- **必要な既存コードの変更**: `checkin.add_contact()` が `evacuees.updated_at` を進めている（`checkin.py` 末尾）。このままだとメモが常に `updated_at` 以下の時刻になり、対応済みにならない。**メモを書いても `updated_at` を触らない** ように変える（受付画面の「最近の 8 件」の並びがメモで動かなくなるだけ）
- **メモを書いたら、その人の未対応の相談も対応済みにする**（`add_contact` の中で `chat_logs.status='done', handled_at=now` を `evacuee_id` で更新）。1 回の操作で一覧から消え、デモの筋「対応メモで消える」が単純になる（未決 §9・推奨は「する」）

## 4. 内訳の自動集計（`stats.breakdown(rows)`）

`rows` は `active_evacuees()`（在所中の世帯）。人数は `hh` の合計（`summary()` と同じ数え方）。

### 4.1 想定地区の住民の割合 `area`

- 設定 `area_towns`: 町名をカンマ区切り。**既定 `東野田町,Higashinoda`**（デモの避難所＝東高等学校の所在地。英語住所も拾う）。設定画面「避難所と Wi-Fi」に 1 欄足す
- 判定: `addr` を NFKC 正規化して空白を落とし、町名のどれかを **含む** なら区内。`addr` が空なら「住所なし」。それ以外は「想定地区外」
- 出力:

```python
"area": {"towns": ["東野田町", "Higashinoda"],
         "in":  {"households": 8, "people": 18}, "out": {"households": 4, "people": 8},
         "unknown": {"households": 0, "people": 0},
         "in_pct": 69}        # 人数ベース・整数%。在所 0 人なら None（例は seed_demo の 12 世帯 26 人）
```

- 画面: 「想定地区（東野田町）の住民 **69%**（18 人／8 世帯）・区外 8 人／4 世帯・住所なし 0」。よそから来る人がどれだけいるかは、久保さん（メンター）の話にもある観点（保管庫）

### 4.2 日本語以外を使う人 `non_japanese`

- 世帯の `lang` が `ja` 以外 **または** 伝えたいことに `language` がある世帯。人数はその世帯の `hh`（同行者の言語は取っていないので世帯単位）
- 見出しは **「日本語以外」**（「外国の方」とは書かない。国籍は取っていない）
- 出力: `"non_japanese": {"households": 2, "people": 3, "by_lang": {"en": 3}}`

### 4.3 支援が要る世帯 `needs`

- `by_need`: 伝えたいこと 10 択ごとの世帯数（`NEEDS` の順）
- `households`: 伝えたいことか要配慮（本人・同行者）のどちらかがある世帯数
- `people_with_care`: 要配慮のある人の数（`summary()["care_people"]` と同じ値。重複して数えない）

```python
"needs": {"households": 9, "people_with_care": 10,
          "by_need": {"dialysis": 0, "oxygen": 1, "medicine": 3, "doctor": 1, "mobility": 2,
                      "baby": 2, "diet": 3, "family": 1, "sleep": 1, "language": 2}}
```

### 4.4 受付の方法 `source`

- `{"app": 9, "manual": 3, "qr": 0}`（世帯数）。「避難者が自分で登録した割合」がそのまま「運営の手間が減った」の説明になる

## 5. 画面

### 5.1 ダッシュボード `/staff`（順番を変える）

1. **対応の優先順**（新規・先頭）: レベル別の件数チップ（至急 1・急ぎ 3 …）→ 上位 **10 行**（レベル色・受付番号・氏名（人数）・理由チップ・待ち時間・「対応メモ →」）。匿名相談は「匿名」表示で「避難者の声で対応済みにする →」。0 件なら「いま対応を待っている人はいません」。「全件を見る →」で `/staff/priority`

4. 不足物資・避難者の声・お知らせ・システム（既存のまま）
5. 30 秒ごとの自動更新はそのまま

### 5.2 全件 `/staff/priority`（新規ページ）

- 一覧の全行。レベルで絞り込み（`?level=5`）、「対応済みも見せる」（直近 24 時間に消えた行。任意・後回し可）
- 各行の「対応メモ」は個人ページへ飛ぶだけ（一覧の中でメモを書くフォームは作らない。既存の導線を使う）

## 6. 本部へそのまま渡す（`eei.json`）

`stats.eei()` に **氏名を入れずに** 足す（仕様書 §11・国へ上がるのは集計値だけ）。`v` は 1 のまま（追加のみで互換）。

```json
"area": {"towns": ["東野田町", "Higashinoda"], "in_households": 8, "in_people": 18, "out_people": 8, "unknown_people": 0, "in_pct": 69},
"non_japanese": {"households": 2, "people": 3, "by_lang": {"en": 3}},
"needs": {"households": 9, "by_need": {"oxygen": 1, "medicine": 3, "...": 0}},
"priority": {
  "levels": {"5": 1, "4": 3, "3": 2, "2": 3, "1": 0}, "open_total": 9,
  "top": [ {"id": 5, "level": 5, "reasons": ["need:oxygen", "care:MED", "need:medicine"], "since": "2026-09-25T13:02:00+09:00"} ]
}
```

- `top` は **受付番号と理由コードと時刻だけ**（氏名・備考・相談の本文は入れない）。氏名は名簿 CSV で既に渡している
- 同期画面 `/staff/sync` に「送る中身のプレビュー」（`eei.json` を整形して表示）を足すと「人に渡せる」が見える（任意）

## 7. テスト（`scripts/shelter_smoke.py` に足す・AI 抜きで動く）

1. 透析（`needs: dialysis`）の自己登録が、擦り傷（`care: ILL` だけ）の手入力より上に並ぶ
2. 同行者に `NUR` がある世帯が、理由に「同行 …」付きでレベル 3 以上になる
3. 想定地区の割合: `東野田町` の住所 2 件・`網島町` 1 件・住所なし 1 件 → `in_pct` が人数ベースで合う
4. 日本語以外: `lang: en` の世帯と `needs: language` の世帯が `non_japanese` に数えられ、二重に数えない
5. 個人ページで対面対応のメモを書く → その人の行が `priority.items()` から消える → 本人がスマホから内容を直す（`POST /register` 再送）→ 再び出る
6. ガードに掛かった登録者の相談が、その人の行のレベルを 5 にする。メモを書くと相談も `done` になる（§3.4 を採る場合）
7. 匿名端末の緊急相談が「匿名」の別行で出る
8. `eei.json` の `priority.top` に `name` が無く、`levels` の合計が `open_total` に一致する
9. `/staff` と `/staff/priority` が 200 で、先頭に「対応の優先順」がある
