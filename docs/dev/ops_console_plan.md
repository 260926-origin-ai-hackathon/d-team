## 0. 結論（何をどう変えるか）

- **データ**: 「世帯（名簿）」と「**案件**（申告・伝言・相談・聞き取りの 1 本のストリーム）」と「**記録**（案件と人に付く時系列の出来事）」の 3 表にする。避難者の「伝える」も、登録時の「伝えたいこと」も、チャットの要望も、職員が対面で聞いた困りごとも、**同じ形の案件**として入る。優先順・受信箱・個人ページ・本部への集計は全部この表から出す
- **運営画面**: 7 タブ。**いま**（誰から対応するか）／**対応**（読み取って聞き取って更新する）／**案件**（受信箱型のトリアージ）／**人**（名簿）／**お知らせ**／**物資**／**本部へ**（＋設定は右上の歯車）
- **トリアージ**: レベルは自動（登録内容のルール）＋手で上書き。状態は 未対応 → 対応中 → 保留 → 済み の 4 つ。再オープンは本人の再送で自動。並びは「レベル → 待たせている時間」、目安時間を超えたら赤くする。「トリアージ」「黒タグ」の語は使わない
- **記録**: 案件にも人にも同じ「1 本の時系列」。定型文ボタンで「メモ＋状態変更」を 1 クリック。時刻・担当は自動
- **避難者側**: 「避難所に伝える」（用件 1 つ＋急ぐ＋自由記述）。送ったものは本人の画面に **受付済 → 対応中 → 対応済** で見える（デジタル庁の実証で運営者が「対応状況が見えると安心」と答えた点に合わせる）

## 1. リサーチの要点（設計に効いたものだけ・出典付き）

### 1.1 問い合わせ・案件を捌くツール（Zendesk／Intercom／Help Scout／Front／Linear／Jira SM）

| 観察 | 採る／採らない |
|---|---|
| 状態は「未対応 / 対応中 / 待ち / 済み」の 4 段が最小公倍数。Zendesk は New/Open/Pending/On-hold/Solved/Closed の 6 つ、Help Scout は Active/Pending/Closed の 3 つでカスタム不可 [1][3] | **採る（4 段）**。Closed は人が押さない（Zendesk は Solved から自動 Closed [1]） |
| 再オープンは要望者の返信で自動（Zendesk・Intercom・Help Scout 共通）[1][2][3] | **採る**。本人が同じ用件を再送したら open に戻す |
| Intercom は優先度が「フラグ 1 個」、Help Scout は優先度を持たず「待たせている時間」だけで並べる。内部メモは待ち時間をリセットしない [2][3] | **一部採る**。少人数には「段階＋経過時間」で十分。内部メモで待ち時間を止めない |
| Zendesk の SLA バッジは 緑 → 残り 15 分で琥珀 → 超過で赤 [4] | **採る**。レベルごとの目安時間（§3.3）で色を変える |
| Linear の Triage Inbox: 受理(1)／重複(2)／却下(3)／スヌーズ(H) を数字キーで。受理時に優先度と担当を同時に付けて「二度目のトリアージ」を防ぐ [5] | **採る**。受信箱で 1=対応中・2=済み・3=保留、j/k で移動 |
| 一覧の型: 受信箱型（左一覧・右詳細）は往復のある案件向き。表型は分類軸が多いとき。かんばんはドラッグが要り、状態が 3〜4 段だと列が薄い [6] | **受信箱型**を採る（1〜3 人・PC 1 台・時間が無い） |
| 内部ノートは黄色、返信はグレー、状態変更も同じ時系列に流す（Help Scout・Intercom）[3] | **採る**。案件と人の画面に 1 本のタイムライン |
| 通知は バッジ（件数）→ 上部バナー（時間制約）→ モーダル（最緊急のみ）の段階付け [7] | **採る**。緊急（ガード）は上部バナー、未対応数はタブのバッジ |

### 1.2 医療トリアージの転用

- START 法は 赤/黄/緑/黒、JTAS は 青/赤/黄/緑/白 で体系により色の順が違う。JTAS は各レベルに「診察までの目安（直ちに / 10 分 / 30 分 / 1 時間 / 2 時間）」と再評価間隔が付く [8][9]
- 避難者と医療者が同じ画面を見る可能性があるので、**黒タグ・「トリアージ」の語は使わない**。借りるのは「目安時間と再評価」だけ。色は 3 色までに留める

### 1.3 現場で「その場で書く」ための工夫（介護・訪問看護・コールセンター）

- 「選択肢＋数値＋補足」の 3 層テンプレートで入力 4 分 → 90 秒。定型文タップ、時刻自動、**入力途中でも常時保存**、音声入力 [10][11]
- 用件分類（後処理コード）は **10 前後まで**。多いと先頭や馴染みのコードに偏る。「その他」は自由記述を許し、頻出したら分類に昇格 [12]

### 1.4 バーコードで本人の記録を開く

- **USB リーダー（HID）** は文字列をキー入力として一気に送り末尾に Enter。罠は「フォーカスが無いと入力が消える」「paste では拾えない」「配列の不一致で記号が化ける」。対策は document 全体の keydown で「30〜50ms 間隔の連続入力＋Enter」を検出 [13]
- **ブラウザのカメラ読み取りは Windows では実質使えない**（BarcodeDetector API は macOS・Android のみ。ZXing-js はメンテ終了）[14][15] → 運営 PC は **USB リーダー一択**。同梱した `zxing.min.js` は使わない
- 病院はリストバンド＋**本人に名乗ってもらう**の二重確認。イベント受付は 1 人 5〜10 秒、読めないときの**氏名検索の代替導線**が必須 [16][17]

### 1.5 避難所運営の実態と既存の仕組み

- 内閣府の避難者カード標準様式は、要望が **受付時の自由記述 1 欄**だけ。継続的な受付・対応記録の欄は無い [18]
- 能登の実態調査: 毎日 9 時 /16 時の定例会議で困りごとを聞き取り、NPO が各部屋を回って**一覧化して本部へ**。職員ローテで「要望への対応方針が職員ごとに違う」問題 [19] → 対応記録を人に付けて残す価値の裏付け
- **デジタル庁 2024 年度実証（珠洲市）**: 避難者がスマホから**選択式で体調・不足物資を運営に報告**。利用者は「選択式で簡単に伝えられ安心」「一人避難でも存在を把握してもらえる」、運営者は「**確認済みだけでなく対応中／対応済みが見えると安心**」[20]
- 石川県の被災者データベース（Palantir）は名寄せと閾値アラートが中心で、避難者からの伝言を受ける機能は資料に無い [21]。国内の避難所向け製品も受付・名簿が中心で、避難者→運営の連絡機能は見当たらない（未確認）
- 現場で実際に聞き取られている項目: 服薬中の薬名と残り日数・通院先・介助・車いす・アレルギー・乳幼児用物資・家族の安否/未連絡者・居場所の希望（教室・福祉スペース）・退所先と時期・安否情報の公開可否 [18][19][22]

## 2. データ設計（世帯 ＋ 案件 ＋ 記録）

### 2.1 3 つの表

```
evacuees（世帯・人。いまのまま）
   │ 1
   │
   ├── 多  cases（案件）        ← 登録時の申告・「伝える」・チャットの要望・職員の聞き取り。1 件＝運営が対応すべき 1 つのこと
   │
   └── 多  events（記録）       ← 案件と人に付く時系列。対面対応のメモ・状態の変更・本人の再送・受付・退所
```

**`cases`（案件）**

| 列 | 中身 |
|---|---|
| `id` | 案件番号 |
| `evacuee_id` | 受付番号。匿名端末のチャットだけ NULL |
| `source` | `register`（登録時の伝えたいこと）／`message`（避難所に伝える）／`chat`（チャットの要望・困りごと・緊急）／`staff`（職員が対面で聞き取った） |
| `category` | 統一分類 8 種（§2.2） |
| `detail` | 元の細かい値（`needs` のキー・`topic`・「伝える」の用件） |
| `text` | 本文（申告の表示名・伝言・発言・聞き取り） |
| `lang` | ja / en |
| `level_auto` | 5〜1（ルールで決める。§3.3） |
| `level` | 表示に使うレベル。職員が上書きしたらその値、無ければ `level_auto` |
| `status` | `open`（未対応）／`in_progress`（対応中）／`hold`（保留）／`done`（済み） |
| `hold_reason` | 保留の理由（「保健師の巡回待ち」など。誰待ちかを書く） |
| `assignee` | 担当（職員名の自由記述。空でよい） |
| `next_check_at` | 次に確認する時刻（任意。過ぎたら「いま」に出す） |
| `created_at` / `updated_at` / `handled_at` | 発生・更新・済みの時刻 |
| `chat_log_id` | `chat` 由来なら元の発言 |

**`events`（記録・タイムライン）**

| 列 | 中身 |
|---|---|
| `id`, `evacuee_id`, `case_id`（任意） | 誰の・どの案件の |
| `kind` | `note`（対面対応のメモ）／`status`（状態の変更）／`message`（本人からの伝言）／`chat`／`checkin`／`checkout`／`edit`（登録内容の変更）／`resend`（同じ用件の再送） |
| `text` | メモ本文・変更の内容 |
| `actor` | `staff`（職員名があれば）／`evacuee`／`system` |
| `created_at` | 時刻（自動） |

いまの `contacts` は `events(kind='note')` に、`chat_logs.status/handled_at` は `cases.status` に移す（`chat_logs` は発言の記録として残す。質問の統計はこれまでどおり `chat_logs` から）。

### 2.2 統一分類（8 種）と用件

| 分類 | 避難者の「伝える」用件 | 登録時の needs | チャットの topic | 参考: 要配慮（属性） |
|---|---|---|---|---|
| 医療・体調 | 体調が悪い・薬が要る | dialysis・oxygen・medicine・doctor | medical | MED・ILL |
| 介助・移動 | 移動や介助の手助け | mobility | staff（一部） | NUR・DIS |
| 乳幼児・妊産婦 | 粉ミルク・おむつ | baby | baby | INF・PRG |
| 食事・水 | 食事・水のこと | diet | food・water | ALG |
| 生活環境 | トイレ・寝る場所・寒い暑い・充電 | — | toilet・bath・bedding・env・charge・facility | — |
| 安全・不安 | 怖い・不安・眠れない | sleep | safety | — |
| 家族・安否 | 家族と連絡が取れない | family | family | — |
| その他・手続き | 帰宅・退所の予定／言葉／その他 | language | info・procedure・pet・other | — |

- 用件は **8 個・1 つだけ選ぶ・「その他」を必ず置く**（後処理コードの知見 [12]）。頻出した「その他」は分類に昇格させる
- 「急ぐ」は用件とは別のトグル。暴力・急病の言葉は既存のガードと同じく AI もキューも通さず、窓口の案内を返して案件を **緊急（レベル 5）** で立てる
- 色は 8 分類に固定し、`tag`・`chip` の色を全画面で揃える

### 2.3 いまのデータからの移行（起動時に 1 回・`voices.backfill()` と同じ方式）

1. `evacuees.needs` → `cases(source='register')`。世帯ごと・needs 1 つにつき 1 件。`created_at` は `checked_in_at`
2. `chat_logs` の `kind ∈ {request, trouble, emergency}` → `cases(source='chat')`。`status` は `chat_logs.status` を引き継ぐ
3. `contacts` → `events(kind='note')`。そのメモの時刻より前に開いていた同じ人の案件は `done` にする（いまの「メモで消える」と同じ結果）
4. `priority.items()`・`breakdown().needs`・`eei()` の `needs`／`priority` を `cases` から出すように書き換える（画面の結果は変わらない）

### 2.4 「1 個のデータセット」として渡す形

- 名簿 CSV（標準様式・1 人 1 行）はそのまま。列「未対応の案件（分類・レベル・発生時刻）」を足す
- 新規 `cases.csv`（本部の保健・福祉班向け。受付番号・分類・レベル・状態・発生・済み・担当。本文と氏名は入れない）
- `eei.json` に `cases: {by_category × status, by_level}` を足す

## 3. 運営画面（7 タブ）

### 3.1 タブ

| タブ | 問い | 中身 | いまの画面から |
|---|---|---|---|
| **いま** | 誰から対応するか | 数字 4 枚（在所人数・未対応・目安超過・不足の品目）＋ 対応の優先順 上位 10（人単位）＋「次に確認する時刻が来た人」＋ 最新お知らせ 3 件。**内訳や要配慮の表は出さない** | ダッシュボードを削る |
| **対応** | この人に何をするか | §3.4。読み取り → 本人確認 → 未対応の案件 → 聞き取り → 更新 | 新規。受付（手入力）もここの「＋職員が登録」 |
| **案件** | 何が来ていて、どれからか | §3.5。受信箱型。未対応／対応中／保留／済みのタブ、分類・出どころで絞り込み、右に詳細とタイムライン | 避難者の声＋対応の優先順の全件を統合 |
| **人** | 誰がいるか | 名簿一覧（絞り込みチップ: 対応待ち／要配慮／日本語以外／想定地区外／退所）→ 個人ページ（§3.6） | 名簿＋AI 助手②要配慮者 |
| **お知らせ** | 何を伝えるか | 投稿・英訳・一覧。案件の「お知らせにする」から見出し付きで来る。「質問と多い声」（チャットの質問の統計・答えられなかった質問）をここの右側に置く | お知らせ＋避難者の声の質問部分 |
| **物資** | 何が足りないか | 不足の目安・備蓄量の入力・AI 補足 | ダッシュボードのカード＋設定の備蓄＋AI 助手③ |
| **本部へ** | 何を報告するか | 内訳（想定地区・日本語以外・支援が要る世帯）・`eei.json` のプレビュー・送信・CSV 2 種 | 本部へ送る＋内訳 |
| ⚙ 設定 | — | 避難所・Wi-Fi・QR・想定地区・マニュアル・白紙化・AI | 設定＋システム状態 |

AI 助手はタブから外す。①マニュアル検索は右上の常設ボタン、②要配慮の要約は「人」、③物資の補足は「物資」、④掲示文は「お知らせ」、⑤引継ぎは「いま」の「引継ぎメモを作る」。

### 3.2 全画面共通のルール

1. 1 画面 1 つの問い。答えにならない表は置かない
2. **人の行は 1 部品**（レベル色・受付番号・氏名（人数）・分類チップ・経過時間・アクション）。いま・案件・人・対応で同じ見た目
3. **案件の行も 1 部品**（レベル・分類・本文の先頭・誰・経過・状態ボタン）
4. **タイムラインは 1 部品**。人の画面では全案件の記録が時系列に混ざる。案件の画面ではその案件だけ。内部メモは黄色の背景
5. 状態の変更は **1 クリック**（行の右端に「対応中」「済み」「保留」）。定型文ボタンは「メモを残す＋状態を変える」を同時にやる
6. 未対応の件数はタブのバッジ、緊急（ガード）は上部バナー。音は鳴らさない（未確認のため）
7. 30 秒の自動更新は続けるが、**入力中の画面は更新しない**（対応・案件の詳細を開いているとき）
8. 「トリアージ」「黒タグ」の語は使わない。「対応の優先順」「レベル」「目安」で統一

### 3.3 レベル・目安時間・並び

| レベル | 表示 | 色 | 目安（この時間までに誰かが見る） | 超過の表示 |
|---|---|---|---|---|
| 5 | 至急 | 赤 | 10 分 | 経過時間を赤く・上部バナー |
| 4 | 急ぎ | 橙 | 1 時間 | 経過時間を赤く |
| 3 | 今日中 | 黄 | 当日中（22 時まで） | 経過時間を橙 |
| 2 | 様子見 | 緑 | 24 時間 | 経過時間を橙 |
| 1 | 声かけ | 灰 | 無し | — |
